# data/seed — curated verified incidents (owner: P1)

| File | What it is |
|------|------------|
| `curated_incidents.yaml` | **Human-edited source.** 60 resolved incidents, 2 per ticket subcategory (6 categories × 5 subcategories). |
| `resolved_incidents.json` | Generated by `python -m ingest.make_seed`. `INC-H0001…INC-H0060`, `resolution_origin = "curated_verified"`, `verified = true`, indexed into the `tickets_verified` Chroma collection by `make data`. |
| `test_seed.json` | Hand-written test and trial tickets used by `make test-sets` (P1-T5). |

These incidents are the **only** historical items the engine may cite as a `"Historical Incident"`
source (architecture §6.3.2) until analysts verify more resolutions in the app
(`TicketStore.mark_verified()` → `analyst_verified`). Synthetic resolutions in `tickets_hist` are
shown to analysts but never cited.

## Provenance

The 60 incidents were **drafted with AI assistance** (`drafted_by` in the YAML) from the KEDB
runbooks and realistic service-desk patterns, then attributed to the P1 owner as reviewer
(`verified_by`). Each record carries `metadata.review_status`; it starts as
`pending_human_review`. **A person must go through the checklist below and set
`review_status: reviewed` before the demo.**

## Review checklist (per incident)

- [ ] The title and description read like a real user ticket; no real names, emails or IDs.
- [ ] The category/subcategory is right for the description.
- [ ] The resolution is concrete (what was wrong, what was done, how it was confirmed).
- [ ] The resolution is consistent with the cited KB article(s) in `kb_ids`.
- [ ] It follows the KB safety rules: no disabling security controls, no sharing passwords,
      no broad privilege grants, no destructive steps (enforced by `make_seed` and tests).
- [ ] Admin-only actions are done by the right team (DBA, network ops, security, desk-side).
- [ ] Priority is plausible for the impact described.

After editing the YAML: `python -m ingest.make_seed && make data && make test-p1`.
